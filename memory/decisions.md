# decisions — журнал решений (ADR-стиль)

Каждая запись: решение, контекст, последствия. Пополняется по ходу работы.

## ADR-001: docs/ — стабильное знание, memory/ — изменчивое состояние

- **Статус**: принято (2026-08-17)
- **Контекст**: правила лежали в двух местах (.clinerules + AGENTS.md) и
  расходились; агент не отличал знание о системе от текущего состояния работы.
- **Решение**: `docs/` — пять категорий (architecture, design-docs,
  execution-plans, technical-debt, principles) для стабильных фактов о системе;
  `memory/` (active-context, progress, decisions) — изменчивое состояние работы.
- **Последствия**: AGENTS.md ссылается на оба каталога условиями-указателями;
  правило, встреченное дважды, выносится в docs/, а не повторяется в промпте.

## ADR-002: корневой AGENTS.md — карта, а не энциклопедия

- **Статус**: принято (2026-08-17)
- **Контекст**: AGENTS.md разросся до «кладбища правил» (graveyard of stale rules).
- **Решение**: ≤100 строк. Схема БД, конвенции кода и история решений — только в
  `docs/`; в AGENTS.md остаются условия-указатели на них.
- **Последствия**: при изменении фактов правится docs/, AGENTS.md меняется редко.

## ADR-003: вложенные AGENTS.md рядом с сервисами

- **Статус**: принято (2026-08-17)
- **Контекст**: правила Monitor/Worker были размазаны по .clinerules и корневому
  файлу; агент читает ближайший к рабочей директории файл инструкций.
- **Решение**: короткие AGENTS.md в `src/newsmill/{monitor,worker,common}/`;
  корень их не дублирует.
- **Последствия**: работа внутри сервиса поднимает только локальные правила.

## ADR-004: .clinerules удалён, контент разнесён

- **Статус**: принято (2026-08-17)
- **Контекст**: два источника правды (.clinerules и AGENTS.md/docs) гарантированно
  расходятся.
- **Решение**: 06-monitor → `monitor/AGENTS.md`; 12/13 → `worker/AGENTS.md`;
  02/03/04/09/10/11/14 → `docs/principles/coding-standards.md`; остальное уже
  покрыто docs/ → удалено. Каталог `.clinerules/` удалён целиком.
- **Последствия**: единственный источник правил — AGENTS.md + docs/ + memory/.

## ADR-005: ближайшая доработка — дедупликация GUID в PostgreSQL

- **Статус**: принято (2026-08-17)
- **Контекст**: known-issues #1 — `seen_guids` в памяти Monitor, после рестарта
  дубли снова публикуются в очередь.
- **Решение**: оформить как execution-plan 001; задача — перенести состояние
  дедупликации в PostgreSQL.
- **Последствия**: план 001 (`docs/execution-plans/001-dedup-postgres.md`) —
  следующий блок работ после реорганизации документации.

## ADR-006: дедуп в отдельной таблице `processed_items`, а не в `news.link`

- **Статус**: принято (2026-08-18)
- **Контекст**: выбор хранилища признака обработки GUID (шаг 2 плана 001).
- **Решение**: таблица `processed_items` (PK по `guid`, `created_at`); claim
  атомарным `INSERT ... ON CONFLICT (guid) DO NOTHING RETURNING`
  (`monitor/dedup.py`). Альтернатива — подзапрос к `news.link` — отклонена:
  `news` не хранит `guid`, и проверка по `link` путала бы «опубликовано» с
  «сохранено воркером» (published-but-not-persisted GUID повторно публиковался
  бы после рестарта).
- **Последствия**: Monitor получает зависимость от PostgreSQL (что и 
  фиксирует ADR-007); таблица растёт без очистки → known-issues #7.
- **Поведение при сбое БД**: claim падает — запись всё равно публикуется
  (at-least-once); финальный гейт от дублей — `UNIQUE` на `news.link` у воркера.
  Соответствует core-belief «сбой не роняет систему».

## ADR-007: общие движок/сессии БД — в `common/db/session.py`

- **Статус**: принято (2026-08-18)
- **Контекст**: раньше движок/сессии жили только в `worker/database.py`, а
  Monitor БД не касался вовсе. После ADR-006 Monitor нуждается в движке.
- **Решение**: перенести `get_engine`/`get_session_factory`/`get_session`/
  `close_engine` в `common/db/session.py`; `worker/database.py` стал тонким
  re-export (обратная совместимость, `worker/app.py` не менялся). Избегаем
  дублирования ~40 строк инфраструктурного кода.
- **Последствия**: контракт сообщения (`NewsItem`) не затронут; оба сервиса
  используют единый session-модуль.

## ADR-008: retention — отдельная purge-команда по DELETE_AFTER

- **Статус**: принято (2026-08-20)
- **Контекст**: known-issues #9 — `news`/`entities`/`processed_items` хранятся
  бессрочно, база неограниченно растёт; #7 (рост `processed_items`) решается
  этим же механизмом.
- **Решение**: `Settings.delete_after_days` из `DELETE_AFTER` (`.env`, default 30);
  `common/db/retention.py` (`purge_old_records`) — одна транзакция: первым
  удаляется `processed_items`, затем `news` (сущности каскадом). Запуск —
  отдельный entrypoint `python -m newsmill.maintenance.purge`, в Docker —
  сервис `maintenance` с профилем `tools` (не поднимается на `docker compose up`).
  Тесты — на in-memory SQLite (`aiosqlite`, dev-зависимость).
- **Последствия**: сервисы не усложняются фоновыми задачами; миграций нет.
  Нюанс: пурдж `processed_items` старше порога может повторно опубликовать GUID
  «ожившей» ленты — дубль блокируется `UNIQUE` на `news.link` у воркера
  (зафиксировано в `data-model.md` §7).
