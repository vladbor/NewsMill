# decisions — журнал решений (ADR-стиль)

Каждая запись: решение, контекст, последствия. Пополняется по ходу работы.

## ADR-001: docs/ — стабильное знание, memory/ — изменчивое состояние

- **Статус**: принято (2026-08-17)
- **Контекст**: правила лежали в двух местах (.clinerules + AGENTS.md) и
  расходились; агент не отличал знание о системе от текущего состояния работы.
- **Решение**: `docs/` — пять категорий (architecture, design-docs,
  execution-plans, technical-debt, principles) для стабильных фактов о системе;
  `memory/` (active-context, progress, decisions) — изменчивое состояние работы.
- **Последствия**: AGENTS.md ссылается на оба каталога условиями-указателями;
  правило, встреченное дважды, выносится в docs/, а не повторяется в промпте.

## ADR-002: корневой AGENTS.md — карта, а не энциклопедия

- **Статус**: принято (2026-08-17)
- **Контекст**: AGENTS.md разросся до «кладбища правил» (graveyard of stale rules).
- **Решение**: ≤100 строк. Схема БД, конвенции кода и история решений — только в
  `docs/`; в AGENTS.md остаются условия-указатели на них.
- **Последствия**: при изменении фактов правится docs/, AGENTS.md меняется редко.

## ADR-003: вложенные AGENTS.md рядом с сервисами

- **Статус**: принято (2026-08-17)
- **Контекст**: правила Monitor/Worker были размазаны по .clinerules и корневому
  файлу; агент читает ближайший к рабочей директории файл инструкций.
- **Решение**: короткие AGENTS.md в `src/newsmill/{monitor,worker,common}/`;
  корень их не дублирует.
- **Последствия**: работа внутри сервиса поднимает только локальные правила.

## ADR-004: .clinerules удалён, контент разнесён

- **Статус**: принято (2026-08-17)
- **Контекст**: два источника правды (.clinerules и AGENTS.md/docs) гарантированно
  расходятся.
- **Решение**: 06-monitor → `monitor/AGENTS.md`; 12/13 → `worker/AGENTS.md`;
  02/03/04/09/10/11/14 → `docs/principles/coding-standards.md`; остальное уже
  покрыто docs/ → удалено. Каталог `.clinerules/` удалён целиком.
- **Последствия**: единственный источник правил — AGENTS.md + docs/ + memory/.

## ADR-005: ближайшая доработка — дедупликация GUID в PostgreSQL

- **Статус**: принято (2026-08-17)
- **Контекст**: known-issues #1 — `seen_guids` в памяти Monitor, после рестарта
  дубли снова публикуются в очередь.
- **Решение**: оформить как execution-plan 001; задача — перенести состояние
  дедупликации в PostgreSQL.
- **Последствия**: план 001 (`docs/execution-plans/001-dedup-postgres.md`) —
  следующий блок работ после реорганизации документации.
