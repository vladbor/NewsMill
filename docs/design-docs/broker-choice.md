# Выбор брокера сообщений: почему RabbitMQ

## 1. Что рассматривали

| Брокер | Вывод | Обоснование |
|---|---|---|
| **RabbitMQ** | **выбран** | Классический брокер сообщений, durable-очереди, публикация/подписка, соответствует задаче «очередь между двумя async-сервисами». |
| **Redis** | отклонён | Это скорее KV-хранилище, а не брокер сообщений. Подходит для кэша/паблиш-сабскрайб, но не обеспечивает надёжных durable-очередей как основной сценарий. |
| **NATS** | отклонён | Технология не знакома автору; добавляет ещё один неизученный инструмент в стек учебного проекта. |

Также учитывалась новизна темы: брокер сообщений — новый для автора навык,
RabbitMQ даёт максимум образовательной ценности при минимуме «граблей».

## 2. Чем платим за выбор

- **Инфраструктура**: RabbitMQ поднимается в Docker Compose
  (`rabbitmq:4-management`), т.е. для локального запуска нужен Docker.
- **Сложность**: появляются два способа сбоя (сеть/брокер) плюс необходимость
  поддерживать контракт сообщения между сервисами.
- **Развязка vs. деббаг**: очередь развязывает жизненные циклы сервисов
  (Monitor и Worker: переживают рестарт соседа), но горизонтальный след сообщения
  сложнее трассировать.

## 3. Как конкурирующие варианты отражены в коде

- Контракт и формат сообщения вынесены в `common/` — при смене брокера меняется
  только слой `publisher.py` (Monitor) и `RabbitBroker` (Worker).
- Очередь durable + delivery PERSISTENT — надёжность сообщений без потерь при
  рестарте брокера.
