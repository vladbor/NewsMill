# Контракт сообщения в очереди RabbitMQ

Очередь — единственный канал связи между Monitor и Worker. Контракт задаёт
общий код для обоих сервисов (`common/models.py`) и обязан соблюдаться при
внесении изменений.

## 1. Физический слой

- Брокер: RabbitMQ. Очередь: `RABBITMQ_QUEUE` (по умолчанию `news`),
  durable (`durable=True`) — переживает рестарт брокера.
- Сообщение: JSON (UTF-8, `ensure_ascii=False`), `delivery_mode=2`
  (PERSISTENT) — `monitor/publisher.py`.
- Публикация через default exchange, routing key = имя очереди.

## 2. Поля сообщения (NewsItem)

| Поле | Тип | Обязательность | Описание |
|---|---|---|---|
| `source` | string | да | Агентство (например «RIA Novosti») |
| `title` | string | да | Заголовок новости |
| `link` | string | да | URL полной статьи |
| `guid` | string | да | Уникальный идентификатор (fallback — link) |
| `published_at` | datetime (ISO 8601) | да | Дата публикации |
| `text` | string | да | Описание/содержимое новости |

## 3. Версия и совместимость

- Сообщение сериализуется из Pydantic-модели (`model_dump(mode="json")`) и
  валидируется обратно строгой моделью (`NewsItem.model_validate`).
- **Правило эволюции**: контракт расширяется только добавлением опциональных
  («ленивых») полей. Жёсткие изменения полей — breaking change: требуют
  синхронного обновления обоих сервисов и фиксации в этом документе.
- Явного числового номера версии в сообщении нет: совместимость обеспечивается
  общей моделью в `common/`.

## 4. Обработка ошибок на стороне Worker

- Ошибки десериализации (не-JSON, не-`NewsItem`) логируются, сообщение
  ack: malformed-сообщение не роняет Worker (poison-pill политика — см.
  `technical-debt/known-issues.md`).
