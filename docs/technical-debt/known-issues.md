# Известные проблемы: сознательно не чиним сейчас

Точка контроля осознанных компромиссов. Если проблема становится критичной —
оформляется как execution-plan и выводится отсюда.

1. **~~`seen_guids` — только в памяти Monitor~~ — решено (`execution-plans/001`)**.
   Дедупликация перенесена в PostgreSQL (`processed_items`): GUID атомарно
   claim-ится `INSERT ... ON CONFLICT DO NOTHING` перед публикацией и переживает
   рестарт Monitor.

2. **`/refresh` создаёт HTTP-клиент на каждый запрос** (`dependencies.py`).
   Для периодических редких вызовов это приемлемо; ввод общего синглтона клиента
   для `lifespan` отложен до появления реальной нагрузки.

3. **Нет dead-letter / retry для очереди**. Ошибочные сообщения (например,
   временная недоступность БД) ack: не теряются, но и не ретраятся. Сейчас
   объем мал, и крафтовый DLX добавит сложности без явной пользы.

4. **Poison-pill обрабатывается упрощённо**. Malformed-сообщение логируется и
   ack (см. `message-contract.md`), без отдельного карантина. Пока источник
   только один (наш Monitor), вероятность появления плохих сообщений низкая.

5. **Миграции не применяются автоматически**. Это осознанный процессный выбор
   (см. `core-beliefs.md`, пункт 4): риск случайного изменения БД ниже ручной
   операцией человека.

6. **Нет retry при недоступной ленте**. В `monitor/polling.py` сбой `fetch_feed`
   (таймаут, HTTP-ошибка, битый XML) логируется, и лента пропускается до
   следующего цикла опроса. Чем рискуем: при длительной недоступности ленты её
   записи не попадают в систему. Почему не чиним сейчас: интервал опроса — 5
   минут, для учебного проекта достаточно одного цикла; retry с экспоненциальной
   паузой добавит сложности без заметной пользы.

7. **~~`processed_items` растёт без очистки~~ — решено (`execution-plans/003`)**.
   Вместо бессрочного хранения заclaimed GUID вводится purge-процедура:
   записи старше `DELETE_AFTER` дней удаляются (см. #9).

8. **Логирование сервисов не настраивается**. Оба сервиса используют только
   `logging.getLogger(__name__)` — корневой конфигурации логгера нет. Monitor
   (uvicorn) выводит в stdout только собственные логгеры `uvicorn.*`, при этом
   INFO-записи `newsmill.monitor.*` не видны; Worker (FastStream) пишет только
   в stdout. Нет: записи на диск, ротации логов, syslog. Чем рискуем: следы
   внутри контейнера теряются с рестартом, локальная диагностика затруднена
   (INFO-события не попадают в docker-логи). Почему не чиним сейчас: для
   учебного проекта stdout достаточно, а единый механизм (файл + syslog)
   оформлен как `execution-plans/002`.

9. **~~Нет процедуры удаления устаревших записей (retention)~~ — решено
   (`execution-plans/003`)**. `news`, `entities` и `processed_items` хранились
   бессрочно. Реализована purge-команда `python -m newsmill.maintenance.purge`:
   записи старше `DELETE_AFTER` дней (`.env`) удаляются одной транзакцией
   (`common/db/retention.py`, сущности — каскадом). Нюанс: после удаления
   `processed_items` GUID «ожившей» ленты может быть опубликован повторно, но
   дубль блокируется `UNIQUE` на `news.link` у воркера.
